**ВЕРДИКТ.** Безусловное одобрение не даю: в новых изменениях есть ошибки сопоставления цветов GPX и позиционирования карты после загрузки проекта. Разделение `listing_busy` / `bundle_busy` само по себе выглядит обоснованным, но утверждение о безопасности `.part` требует оговорки. Ниже отдельно отмечены дефекты, существовавшие до `7396ed1`.

**БЛОКИРУЮЩЕЕ**

- **P1 — разные файлы используют один временный путь; унаследованный дефект.** `lizaalert.rs:1315`: `with_extension("part")` превращает и `sheet.map`, и `sheet.ozf2` в `sheet.part`. Если такие файлы скачиваются параллельно, workers открывают и перезаписывают один файл; после переименования другой worker может продолжать писать уже в опубликованный файл. Параллельный запуск есть на `lizaalert.rs:870`, переименование — на `lizaalert.rs:1417`. Поэтому атомарное переименование здесь **не гарантирует корректность содержимого**. Схема имени существовала до диапазона, новый retry/resume её сохранил. Нужно добавлять `.part` к полному имени, сохраняя исходное расширение.

**СЕРЬЁЗНОЕ**

- **P2 — второй проход GPX не ограничен настоящими треками и их расширениями.** `gpx.rs:246`. Учитывается только `local_name`: любой вложенный `<x:trk>` добавляет слот, а любой `<x:DisplayColor>` записывает цвет в последний слот даже после закрытия настоящего `</trk>`. Условие: GPX содержит такие элементы внутри произвольных `extensions`. В первом случае сопоставление с `gpx.tracks` сдвигается; во втором чужое расширение перекрашивает последний трек. `declared_flags` затем закрепляет ошибку как явно объявленный цвет, поэтому палитра её не исправит. Одинаково затрагивает отдельный GPX и GPX внутри ZIP. Нужна проверка пути элемента, глубины и namespace.

- **P2 — автоматическое позиционирование может пропустить все точки загруженного проекта.** `MapView.svelte:1374`. `focusAllData()` ждёт GeoJSON треков, но координаты точек берёт из уже нарисованных `waypointMarkers`. Их отдельная загрузка ожидает `getWaypoints()` на `MapView.svelte:551`. Если GeoJSON приходит раньше точек, проект только с точками получает пустые bounds и камера остаётся на месте; при переключении проектов могут использоваться маркеры предыдущего проекта. Запрос уже погашен на строке 1404, повторного позиционирования после появления маркеров нет. Следует дождаться данных нужного проекта, а не читать промежуточное состояние отрисовки.

- **P1/P2 — защита поколением охватывает не все асинхронные записи; унаследованные дефекты.**
  - `stores.ts:114`: два пересекающихся `refresh()` безусловно вызывают `set(state)`. При обратном порядке ответов старое состояние заменяет новое. Изолированная проверка исходной функции подтвердила результат: после ответа версии 2 поздний ответ версии 1 оставляет версию 1.
  - `MapView.svelte:370`: проверка режима редактирования выполняется только **до** `await`. Если выключить режим или выбрать другой трек во время запроса, поздний ответ снова создаёт редактируемые маркеры старого трека. Изолированная проверка подтвердила вызов отрисовки после выключения режима. Обработчики маркеров сохраняют старые `layerId`/`trackId`.

  Добавленный `trackGeometryRuns` на строке 1133 эти пути не защищает. По `blame` оба дефекта предшествуют диапазону.

- **P2 — готовый файл скачиваемого бандла может попасть в описание другого бандла; унаследованный дефект.** `application/mod.rs:570`. Условие: скачивается A, оператор открывает preview B, у обоих совпадает `file_name`. `note_bundle_file_ready()` обновляет текущий `selected_project` по `ends_with`, без проверки принадлежности файла бандлу. В результате карта B получает `local_path` карты A. Сам `ready_bundle_files` обход каталога не меняет; проблема находится в соседнем обновлении `selected_project`. Нужна идентичность бандла в уведомлении, а не только имя файла.

**МЕЛКОЕ**

- **P2 — некорректное percent-encoding выбрасывает исключение вместо `null`.** `bundle-url.ts:41`. `decodeURIComponent` расположен вне `try`. Вызов настоящей функции с `https://maps.lizaalert.ru/maps/%/` и с окончанием `%D0/` подтвердил `URIError: URI malformed`. Такой вставленный адрес нарушает заявленный контракт распознавания URL; декодирование должно входить в обработку ошибки.

- **P3 — завершение каталога перезаписывает статус активного скачивания.** `application/mod.rs:442`. Условие: обход завершается или отменяется, пока `bundle_busy` остаётся `true`. Безусловный `update_status()` заменяет сообщение скачивания на `Loaded … projects` / `Stopped …`. Флаги разделены правильно, владение общей статусной строкой — нет. Это замечание именно к `status`, не утверждение об исчезновении отдельной полосы прогресса.

**ЧТО СДЕЛАНО ХОРОШО**

- Каждый busy-флаг освобождается завершением своей операции; обход не очищает `ready_bundle_files`, а его токен отмены отделён от скачивания. По рассмотренным методам снятие взаимного запрета не повреждает эти поля.
- При **уникальном временном пути** скачивание действительно пишет через `.part` и публикует результат после завершения записи. Сканеры карт принимают `.map` / `.sqlitedb`, поэтому обычный `.part` картой не становится.
- Ошибка второго XML-прохода возвращает пустой список цветов и не превращает успешный основной разбор в ошибку импорта. Оба пути импорта используют те же исходные байты.
- У палитры нет off-by-one: цвет берётся по числу уже добавленных треков, затем выполняется `AddTrack`. После удаления цвет может повториться: из трёх треков удалить второй, импортировать новый — новый получит цвет оставшегося третьего. Это следствие выбранной политики подсчёта, а не ошибка индекса.
- Импорт папки продолжает работу после ошибки отдельного GPX/PLT и собирает причины в `skipped` (`import.rs:344`). Рассмотренные изменения проекта проходят через `ProjectCommand`; назначение цвета меняет локальный экземпляр до добавления в проект.
- В `default.json` **нет изменений разрешений** относительно базы. ZIP-распаковка проверяет `enclosed_name()` до создания файла (`archive.rs:180`).
- API возвращает `DayExportDto` и `ImportReportDto` через типизированные bindings, без ручного приведения результата к старой строке.

**ЧЕГО НЕ СМОТРЕЛ**

Полный дифф, остальные компоненты, commands/IPC и реализацию undo не обходил. Поэтому потребление обоих DTO за пределами `api.ts` не подтверждаю; `stores.ts` этих DTO не потребляет. ZIP-импорт отдельно остаётся fail-fast на плохой записи — правило продолжения проверено именно для импорта папки.

Rust-находки основаны на коде; воспроизведения повреждения скачивания и гонок в настоящем приложении не запускал. `just ci`, `cargo audit` и `just smoke` не повторял; выполнены только описанные проверки без записи на диск. Дальше перечисленных участков не смотрел.
